# ADR 0018: What the Payload connector may write

## Status

Accepted, 2026-11-13. Extends [ADR 0014](0014-mcp-gateway-worker.md). Tracked in [issue #113](https://github.com/patronage/launch/issues/113).

## Context

`@patronage/mcp-payload` reads through Payload's own MCP server and writes through `payload.apply`, which has two operation kinds, `update_draft` and `create_draft`. They set top-level fields, take rich text as Markdown, and publish only when the operation says `publish: true`. Every write is previewed, approved by a person, run as that person, checked against `updatedAt`, and read back into a receipt. The connector cannot upload or replace media, change one row of a blocks or array field, write a global, unpublish, schedule, restore a version, delete, or pick a locale.

What Payload 4 offers for each of those, read from the published packages (`payload`, `@payloadcms/plugin-mcp`, `@payloadcms/storage-r2` and `@payloadcms/ui` at 4.0.0-beta.6, the version Launch pins, and at 4.0.0-beta.8 and the newest `4.0.0-internal` build from main):

- **REST covers most of it, as the signed-in user.** `PATCH /api/{collection}/{id}` takes `draft`, `locale`, `publishAllLocales`, `unpublishAllLocales`, `trash` and `overrideLock`. The REST handler sends `overrideLock: false`, so a document another editor has open is refused as locked. `POST /api/{collection}/versions/{versionId}?draft=true` restores a version as a draft, and checks update access for each `_status` it writes. `POST /api/globals/{slug}` updates a global. `DELETE /api/{collection}/{id}?trash=true` and a `deletedAt` update move a document to the trash when the collection sets `trash: true`.
- **Arrays and blocks are saved whole.** Every row carries an `id`, but an update replaces the field's whole value. Changing one row means reading the field, changing that row, and sending the field back.
- **Scheduled publishing is a job, and only the admin can queue it.** `versions.drafts.schedulePublish` adds a `schedulePublish` task. The admin queues it through a server function, not REST, with the scheduling user stored on the job. The job runs as that user, with their access. Nothing runs a queued job until something calls `payload.jobs.run()` or `/api/payload-jobs/run`; on Workers that is a Cron Trigger.
- **Uploads.** `plugin-mcp`'s create and update tools take a file as base64, an `externalURL`, or an `uploadReference` from a staged client upload, and its endpoint caps a request at 4 MiB by default. Payload fetches an `externalURL` only when the collection sets `upload.pasteURL.allowList`, through a guard built on `undici` and `dns.lookup`, which workerd does not provide. `storage-r2` stores a file under the collection prefix and its filename. Image sizes come from a transformer package (`@payloadcms/transformer-sharp`), which needs `sharp` and so does not run on Workers; Launch's media collection has no sizes. Replacing the file of a media document without versions deletes the old object. Payload 4's file versioning keeps old objects only for collections with versions, and with R2 it needs S3 credentials.
- **Localization.** Launch configures none. Where a site does, `locale` selects which values a write sets, and `versions.drafts.localizeStatus` keeps `_status` per locale.
- **`plugin-mcp` takes custom tools**, per collection, per global and top level, each with its own access check. Launch already adds three read-only ones. From beta.8 the plugin turns on its own OAuth server by default (`oauth: { type: 'builtin' }`), which lets an MCP client sign in to Payload directly.
- **Content branching is on main and is not in beta.8.** It is marked experimental, with breaking changes allowed in minor releases. Editors work on a named branch and merge selected changes into `main`, and REST selects a branch with `?branch=`. An agent working in a branch a person then merges would fit the approval model well, but it is too early to build on.

The gateway has limits of its own. A run's tool arguments go into the codemode durable log in the gateway's SQLite Durable Object, which holds at most 2 MB in one value. The approval page's Content-Security-Policy is `default-src 'none'`, and the inline card's allowlists are empty, so neither can show an image today. Preview values are cut at 400 characters.

## Decision

1. **Writes stay on Payload's REST API, run as the approver.** Payload's built-in MCP write tools stay off. Every operation in this ADR has a REST route. If a later one has none, `apps/payload` adds a custom MCP tool beside the read-only ones in `mcp-tools.ts`, whose `access` check lets through only requests signed in by the `cloudflare-access-gateway` strategy and which checks the same permission the admin checks. The gateway calls such a tool only from an approved `apply`: `payload.call` keeps its allowlist of read tools, so no client and no script can reach a write that skips the approval step. When the app moves to beta.8 it sets `oauth: false` on the plugin, because Access is the only sign-in Launch ships ([ADR 0011](0011-cms-behind-cloudflare-access.md)).
2. **One `payload.apply`, more operation kinds.** Each new kind keeps the contract the two current kinds have: a person approves it, it runs with the approver's Payload permissions, its preview is bounded and escaped, it is refused when the target changed since the model read it, and it returns a receipt. New kinds make `expected_updated_at` required on every existing target. The receipt adds the Payload version it created and the target's new `updatedAt`. A batch can mix kinds, still one operation per target.
3. **Upload bytes never travel in `apply`'s arguments.** A read-phase call, `payload.stageUpload`, takes a URL on the site's allowlist or base64 up to a cap. The gateway fetches the URL itself, checks the file's real type from its bytes, refuses SVG, makes a thumbnail with the Cloudflare Images binding, and keeps the bytes in its Durable Object under their SHA-256 until the run ends. `apply` names that hash. On approval the file is posted to Payload's own upload route, so Payload's hooks, MIME checks, size limit and `storage-r2` keys apply.
4. **No permanent delete.** The connector can move a document to the trash and take it back out, only in collections that set `trash: true`. Emptying the trash stays in the admin. Media cannot be trashed through the connector until it can show what still uses the file.
5. **The approval surfaces learn three things**, in `@patronage/mcp-core` so WordPress can use them too: a thumbnail beside a media change, a changed row of a blocks or array field shown as that row's fields, and a warning line for operations that change what the public sees at once (publish, unpublish, a global without drafts, trash, a file replacement).
6. **Order of work:** upload media; change rows of blocks and arrays; update a global; unpublish; restore a version; trash and restore; locale on every kind. The order follows what editors ask an agent for most and how much new machinery each needs. Scheduled publish and unpublish is left out and planned on its own ([issue #121](https://github.com/patronage/launch/issues/121)), because it needs Payload's job queue, a migration and a Cron Trigger, and nothing here depends on it.
7. **Branching is watched, not used.** When Payload's content branching is stable, a later ADR decides whether agents write to branches instead of drafts.

## Consequences

- `apps/payload` changes with the connector: `getEditingInfo` reports globals, upload limits, trash, locales and the blocks and array fields; pages and posts turn on `trash`. A site that adopts the published packages needs the same Payload pieces, so they belong in a documented recipe and later in a Patronage Payload plugin.
- The gateway needs an Images binding for upload thumbnails. Without one, `stageUpload` refuses images it cannot show.
- Required `expected_updated_at` on the new kinds, and new receipt fields, are a breaking change to `payload.apply`'s contract. They ship as a minor version while the packages are below 1.0, with a changeset.
- The approval card's script and CSP change, so its resource moves to a new URI and the old one joins `LEGACY_APPROVAL_APP_URIS`, as in issue #90.
- The upgrade to 4.0.0-beta.8, which needs database migrations, comes before the upload work, because beta.8 changed how uploads are processed.
- Unverified on workerd until the first implementation checks it: a multipart upload through REST on the local Payload Worker with R2, unpublish by saving `_status: draft` without `draft=true`, and `data:` images inside the MCP Apps card.
