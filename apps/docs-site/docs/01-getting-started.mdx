Launch is a plain pnpm workspace.

## Prerequisites

| Tool | Version | Used for |
| --- | --- | --- |
| Node | 24.22.1 or later, the floor Payload 4 sets; `.nvmrc` names the major version | Everything |
| pnpm | The version in the root `package.json`'s `packageManager`; `corepack enable` installs it | Everything |
| Git and Bash | Any recent version | `pnpm verify` runs the WordPress deploy kit's shell tests |
| PHP | 8.1 or later on the command line, with the OpenSSL extension | `pnpm verify` lints and tests the WordPress plugins and themes |
| Docker | A running Docker-compatible engine | Only to run the WordPress references, which install WordPress and Composer packages in containers |

Deploying needs a Cloudflare account and the `cf` CLI as well. See [Deploying to Workers](/deploy).

## Install and check

```bash
git clone https://github.com/patronage/launch.git
cd launch
pnpm install
pnpm verify
```

`pnpm verify` is the full gate: a frozen install, then lint, typecheck and tests across the workspace. Run it before you open a pull request. There are no GitHub Actions. Cloudflare Workers Builds runs only part of it before a deploy: the frozen install and lint for the whole repo, then typecheck and tests for the app being deployed and its packages, and none of the PHP checks, because its build image has no PHP. See [Workers Builds](/deploy/workers-builds).

## Run a reference site

Each reference seeds the same demo content. Each app's README has the details.

**Headless WordPress.** WordPress in Docker, and the vinext front-end in local workerd:

```bash
pnpm --filter cms-wordpress-headless run setup   # WordPress, demo content and .env.local
pnpm --filter web-wordpress dev                  # http://localhost:3000
```

**Payload.** One app on local D1 and R2. `vite dev` does not work with Payload yet, so build and preview:

```bash
cd apps/payload
cp .env.example .env                        # then set PAYLOAD_SECRET in .env
cp .env .dev.vars                           # the Worker reads its secrets from .dev.vars
pnpm payload migrate
pnpm seed
pnpm build && pnpm preview                  # http://localhost:4173/admin
```

**Traditional WordPress.** A Timber theme renders the site, in Docker:

```bash
pnpm --filter cms-wordpress-timber run setup   # http://localhost:8090
```

## Check a change in the browser

`pnpm verify` checks dependencies, lint, types and tests, not that a page looks right. Before you open a pull request that changes pages, sections, forms or the admin, drive the change in a real browser and keep the screenshots. The repo's `launch-verify` agent skill does this for the Payload app and the headless WordPress front-end:

```bash
node .agents/skills/launch-verify/scripts/verify.ts --help
```

## Run these docs

```bash
pnpm --filter docs-site dev     # http://localhost:4321
pnpm --filter docs-site build   # static site in apps/docs-site/dist
```

## Dependencies

Versions are pinned exactly, and pnpm only installs versions older than the `minimumReleaseAge` in `pnpm-workspace.yaml`. Update them with the `deps:*` scripts in the root `package.json`, which read the same window.

Dependencies that most packages share, such as React, Vite, Vitest and `@types/node`, have one version for the whole workspace in the `catalog` in `pnpm-workspace.yaml`. A package lists them as `"catalog:"` instead of a version, so they can't drift apart. `@types/node` follows the Node major the repo runs on.

## Rules for contributors

The repo is public, so everything in it must be fit to publish. How to report a vulnerability privately is in [`SECURITY.md`](https://github.com/patronage/launch/blob/main/SECURITY.md). The short version of the rules, from `AGENTS.md`:

- No third-party plugin or vendor code. WordPress plugins and themes come in through Composer; only Patronage's own `patronage-*` code is committed.
- No client references, anywhere. Demo content is invented.
- No Wrangler config files and no GitHub Actions. See [Deploying to Workers](/deploy).
- Shared UI takes plain props and knows nothing about any CMS.
- A pull request that changes what a reader of these docs would run, deploy or decide updates these docs in the same pull request. Spike notes publish themselves; everything else, including a summary of each new decision record, is a page under `apps/docs-site/docs`.
