## Apps

| App | What it is |
| --- | --- |
| `cms-wordpress-headless` | WordPress in Docker as an editor and a WPGraphQL API. It renders nothing public. |
| `web-wordpress` | The vinext front-end for headless WordPress, deployed as a Worker. |
| `payload` | Payload as one vinext app on Workers: the admin, plus front-end pages that read through the Local API. |
| `cms-wordpress-timber` | A traditional WordPress install with a Timber theme. It shares design tokens with the others, not components. |
| `mcp` | The MCP gateway Worker behind Access. Its WordPress connector is built; the Payload connector is next. See [MCP server](/references/mcp). |
| `docs-site` | This site. |

Some of these are still in progress; see [Research](/research) for where each one stands.

## Shared packages

- **`content-model`**: the CMS-neutral shape of a page and its sections.
- **`ui`**: components that take plain props from `content-model`. They know nothing about WordPress or Payload.
- **`adapter-wordpress`** and **`adapter-payload`**: map each CMS's data to `content-model`. See [CMS-neutral sections](/research/cms-neutral-sections).
- **`access`**: provisions the Access applications, calls the CMS through Access, and verifies Access tokens. See [Lock the CMS behind Cloudflare Access](/research/access-lockdown).
- **`sections-preview`**: a parity test and a static page that render the same page from both CMSs side by side.

The gateway lives in `apps/mcp` for now. Splitting it into packages (`mcp-core`, `mcp-wordpress`, `mcp-payload`) published to npm under `@patronage` is planned.

## Where the CMS stops

Each CMS has an adapter that maps its data to `content-model`. Rich text and editor field definitions stay CMS-specific: the adapter renders rich text and passes it to the shared components as children. That keeps `ui` free of any one editor's format.

## Locking the CMS down

The pattern every reference follows:

1. The CMS admin and API are behind a Cloudflare Access application.
2. The front-end Worker reaches the CMS with an Access service token, or (for Payload) through the Local API in the same Worker.
3. The CMS tells the front-end what changed through a signed revalidation request, so public pages stay cached until an edit is published.
