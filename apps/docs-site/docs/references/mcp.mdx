---
title: MCP server
description: One MCP server per site that the team installs once, signs in to with Cloudflare Access, and that changes content as the signed-in person, with an approval step for sites that need one.
---

The gateway is built as three packages, `@patronage/mcp-core`, `@patronage/mcp-wordpress` and `@patronage/mcp-payload`, deployed by `apps/mcp`. They're published to npm under `@patronage`, with `@patronage/access`, so another site installs them rather than copying the code. Tool packs are still to come. The design is in [ADR 0014](https://github.com/patronage/launch/blob/main/docs/adr/0014-mcp-gateway-worker.md).

## What a site's team gets

- **One install.** One Agent Plugin for Claude, Codex or Cursor that carries only the MCP server's URL.
- **Sign-in through Cloudflare Access.** The same Access application that guards the CMS. Reads run as the signed-in person.
- **Writes as the signed-in person.** A change to CMS content is applied when the person asks for it, with their own CMS permissions. A site that needs it can [require approval](#requiring-approval): every change then pauses with a before-and-after for a person to approve, and runs as the approver. Changes to code will go through a pull request.
- **Tools added over time.** New tools ship in the same server, so nobody reinstalls anything.

## How it fits together

| Part | Status and role |
| --- | --- |
| `packages/mcp-core` | Built. The gateway Worker: sign-in, the code-mode runtime, tool catalog, write approval, logging and the connector contract. It names no CMS |
| `packages/mcp-wordpress` | Built. The `wp` connector: WPGraphQL and REST reads, post updates (core fields, ACF fields and registered post meta) and Redirection rules |
| `packages/mcp-payload` | Built. The `payload` connector: reads through Payload's own MCP endpoint (`@payloadcms/plugin-mcp`). Edits and new documents are saved as drafts, or published when the operation asks for it, and rich text can be written as Markdown. It can also upload a file to an upload collection, or replace one, with a thumbnail where approval is required |
| `apps/mcp` | Built. Launch's deployment: it lists the two connectors and holds the Cloudflare config |
| Tool packs | Planned. Typed tools for named workflows, kept in each site's own repository |

The model sees a short tool list: `execute` runs JavaScript against the connectors in a Dynamic Worker, `describe_site` summarizes the content types, `get_run` reports on a run, and `submit_feedback` and `get_feedback` let an agent report a problem with the tools and hear back. On a site that requires approval, a write is approved on a card inside the client, where the client supports MCP Apps, or on a browser page at `/mcp/approvals/:id`. A site depends on the npm packages rather than copying them.

## How a write runs

By default `execute` applies a write as soon as the model's code calls `apply`, and returns the script's result with a receipt for each write, in `receipts`. A site that [requires approval](#requiring-approval) holds the write for a person first. Either way the write takes the path described here; without approval, the person who asked is the approver and nobody is shown the preview.

An approved write runs inside the Durable Object, as the approver. An approval resumes the script from the top, replaying earlier calls from the run's log, so only the approved write runs live: it must match the arguments the approver previewed exactly, and any read later in the script is refused rather than run with the approver's access. Both approval surfaces show it operation by operation: the browser page streams a line as each operation finishes, and the card polls for the same progress. Operations in one batch run two at a time (`APPLY_CONCURRENCY`), and every receipt still lists them in order. That is safe because a batch never touches one post or one redirect source twice.

The sandbox gives the script 60 seconds when it runs and 5 minutes when an approval resumes it to perform the write. Neither is a Cloudflare limit: a Durable Object has no wall-clock limit while its caller is connected, and its CPU limit counts only CPU, which a write spends almost none of while it waits on the CMS. The page streams its answer partly so that the request stays connected for as long as the write takes. A deployment can change either number by overriding `executionTimeoutMs` or `approvalTimeoutMs` on its `BaseGatewayRuntime` subclass.

A preview can show more than text. A change to a media file shows a small thumbnail with the file's type, size and dimensions; a change to one row of a repeating field is labelled by where the row sits; and an operation that changes what the public sees as soon as it is approved (a publish, a file replacement) carries a warning above it. The thumbnail is made by the gateway and sent inline, so neither the page nor the card loads anything from another address. A file to upload is staged in the gateway before approval, at most 10 MB a file and 25 MB a run, and deleted when the run ends.

In Payload, a `patch_rows` operation changes single rows of an array or blocks field, such as one card in a card grid or one section of a page, without resending the field. Each change names its row by id in a path like `layout[id=6650a1f2].cards[id=b7c1].title`, and can set a field, set a rich text field from Markdown, or insert, remove or move a row. The operation must carry the `updatedAt` it read: it is refused if the document has changed since, including between the preview and the approval, and rows it does not name are sent back as they were read.

An `update_global` operation changes a Payload global, such as the site settings. A global that keeps drafts is saved as a draft unless the operation publishes. A global without drafts is live the moment it is saved, so the operation has to say `publish: true`, and the approval warns that the change is live as soon as it is approved. A global another editor has open in the Payload admin is left alone until they finish.

An `unpublish` operation takes a published Payload document off the public site and keeps its content as a draft, the way the admin's Unpublish button does. The approval warns that the public page goes away as soon as it is approved, names the page's path, and says that links to it will 404 unless a redirect covers them. Publishing it again is an `update_draft` with `publish: true` and no fields.

A `restore_version` operation brings back an earlier version of a Payload document, and `restore_global_version` of a global, through Payload's own restore. The whole version comes back as a new draft, and what is published stays as it is unless the operation says `publish: true`. The approval names the version and shows each field the restore changes. A document or global another editor has open is left alone until they finish.

A `trash` operation moves a Payload document to the trash, on collections that keep one, and `restore_from_trash` takes it back out. The gateway never deletes anything for good: emptying the trash stays in the Payload admin. The approval warns that a public page goes away as soon as it is approved and lists documents that point at it through a relationship field. A restored document comes back as a draft unless the operation says `publish: true`.

On a Payload site with locales, an operation can name the `locale` it writes. A localized field then changes for that locale alone, and a field every locale shares changes for all of them; the approval marks each field one way or the other (`title · es only`, `slug · every locale`). Without a `locale` an operation writes the default locale, as before. Publishing is by locale wherever Payload keeps a status for each: `publish: true` publishes the operation's locale, `publish_all_locales: true` beside it publishes them all, and the approval warns that publishing one locale still puts the shared fields live for every locale. An `unpublish` with a `locale` takes that locale down and leaves the others up; where a newer draft changes fields every locale shares, the approval shows them and warns that they go live for the locales that stay published. A locale the site does not have is refused, since Payload would otherwise write the default locale without saying so.

In Payload, `payload.stageUpload` stages the file and `payload.apply` saves it with an `upload_media` or `replace_media_file` operation. The gateway fetches a file by URL only from the hosts the collection's own `upload.pasteURL.allowList` names, over HTTPS, and checks every redirect against that list; a collection with no list takes no files by URL. A file can also be sent as base64 inside the script, which fits about 14 KB, since a script is at most 20,000 characters. The gateway reads the file's type from its bytes, refuses SVG and anything the collection does not accept, and after approval posts the file to Payload's own upload route as the approver. Replacing a file shows at once wherever it is used, so that approval carries a warning. Thumbnails come from the Cloudflare Images binding (`IMAGES`) on the gateway Worker; without it an approval shows the file's type, size and hash and no picture.

A run reports its write apart from its script. If the script times out or throws after the write landed, the result is the write's receipt with a note that the script stopped afterwards, not a failure. If a write stops before it returns a receipt, the receipt is rebuilt from the operations that reported back, its status is `partial`, and the rest are marked `unconfirmed`, meaning they may or may not have landed. `get_run` gives the same summary in `write`.

## Which clients get the approval card

On a site that requires approval, the card is offered only to a client that says it supports MCP Apps. A client can say so in two places: on each request, in the client-capabilities envelope of protocol revision 2026-07-28, or once, in the `initialize` handshake of the earlier revisions. The gateway keeps no session, so it answers `initialize` with an `Mcp-Session-Id` that carries what the client said, and reads that id on the requests that follow.

A client that says nothing gets the approval link and no card. The card's one-time token travels in tool-result `_meta`, and only a client that supports MCP Apps has promised to keep `_meta` away from the model.

## Requiring approval

A site that wants a person to see every change first builds its gateway with `APPROVAL_REQUIRED=true`. Every write then pauses with a before-and-after, and a person approves it on the card inside the client or on the browser page at `/mcp/approvals/:id`. The setting covers the whole deployment: there is no switch per person or per tool. The reasoning is in [ADR 0023](https://github.com/patronage/launch/blob/main/docs/adr/0023-approval-is-opt-in.md).

Only unset, empty and `false` mean "not required". Any other value holds writes, so a typo doesn't drop the approval a site asked for. A deployment that requires approval also needs `APPROVAL_CSRF_SECRET`.

Without it, which is the default:

- `execute` returns the script's result and a receipt for each write. No result is `paused`, and none names an approval link.
- The server lists no approval card and no card tools. `execute` is annotated as a tool that writes, so a client may ask the person to confirm each call.
- The write runs as the signed-in person, so the CMS's own permissions decide what it may change. The gateway builds the same preview it would have shown, and rejects a write it cannot preview.
- One run may make at most 10 writes.
- Nobody sees the before-and-after first. A prompt injection in content the model reads can change the CMS, and drafts and revisions are the safety net. Require approval on a site where that is not enough.

Upgrading from `@patronage/mcp-core` 0.2.0, where every write was held: set `APPROVAL_REQUIRED=true` before the upgrade to keep it that way.

## Installing it on a site

A site's gateway is a small Worker of its own that installs the packages from npm and lists the connectors it needs.

```bash
pnpm add @patronage/mcp-core @cloudflare/codemode
pnpm add @patronage/mcp-payload     # a site with Payload
pnpm add @patronage/mcp-wordpress   # a site with WordPress
```

```ts
import { createWorker } from "@patronage/mcp-core";
import { BaseGatewayRuntime } from "@patronage/mcp-core/runtime";
import { payloadConnector } from "@patronage/mcp-payload";

export { CodemodeRuntime } from "@cloudflare/codemode";

const connectors = [payloadConnector];

export class GatewayRuntime extends BaseGatewayRuntime<Env> {
  protected readonly connectors = connectors;
}

export default createWorker<Env>({ connectors });
```

Copy `apps/mcp`'s `cloudflare.config.ts`, `vite.config.ts` and `scripts/` as the starting point, and drop the bindings for a CMS the site doesn't have. The published `@patronage/mcp-core` already contains the approval card, so the site has no `generate` step. Then:

- **Keep an existing Durable Object class name.** A gateway that already runs with another class name, such as `WordPressRuntime`, names its subclass that and points `GATEWAY_RUNTIME` at it. Cloudflare keys stored runs and pending approvals to the class.
- **Payload** needs `@payloadcms/plugin-mcp` with read tools only and `oauth: false` (from Payload 4.0.0-beta.8 the plugin otherwise runs its own OAuth sign-in for MCP clients, beside Access), plus the `getEditingInfo`, `getPreviewUrl`, `markdownToRichText` and `richTextToMarkdown` tools from `apps/payload/src/mcp-tools.ts` (with `src/lib/editing-info.ts`). `payload.apply` reads `getEditingInfo` before every write and refuses without it. That tool tells the gateway what can be written: drafts, rich text fields, array and blocks fields and what their rows hold, relationship and upload fields, upload limits, globals and locales. `getPreviewUrl` is optional: with it, the approval page links to the front end's draft preview and the receipt carries the link. The users collection adds `accessGatewayAuthStrategy` from `@patronage/access/payload`, so Payload trusts the forwarded sign-in.
- **WordPress** needs the `patronage-access` mu-plugin from `wordpress-shared/patronage-access`, which is not on npm. Copy it into the site's `wp-content/mu-plugins/`. To let `wp.apply` change a plugin's post meta, such as Yoast's `_yoast_wpseo_metadesc`, register the key with `register_post_meta` and `show_in_rest`, with an `auth_callback` that checks `edit_post`. Redirect operations need the Redirection plugin, and the approver needs its capability (`manage_options` unless the site filters `redirection_role`). `wp.apply` can also set an image's alt text, with `fields.alt_text` on `rest_base: "media"`, up to 400 characters.
- **Access applications** can be created with `provisionLockdown` from `@patronage/access/cloudflare`. The gateway's application covers its whole hostname, not just `/mcp*`, so scanner probes are stopped at the edge and never reach the Worker or its logs. Give the gateway a hostname of its own, and put other services, such as a docs site, on theirs. The `access:provision` command runs only inside the Launch repo.
- **Logging**: `@patronage/launch-logging` is on npm for the Worker wrapper and the `@patronage/launch-logging/cloudflare` helpers. The `logging:provision` command runs only inside the Launch repo.

## Releasing the npm packages

`@patronage/access`, `@patronage/launch-images`, `@patronage/launch-logging`, `@patronage/launch-wpgraphql`, `@patronage/mcp-core`, `@patronage/mcp-payload` and `@patronage/mcp-wordpress` are versioned with [Changesets](https://github.com/changesets/changesets). Each package's `CHANGELOG.md` says what changed in each version and ships in the npm package.

1. A pull request that changes a published package's `src/` or `package.json` adds a changeset: run `pnpm changeset`, pick the packages and the bump, and write the changelog line. While the packages are 0.x, a change that can break a site is a minor bump and anything else is a patch. `pnpm verify` runs `pnpm release:check`, which fails when such a change has no changeset.
2. To cut a release, run `pnpm changeset version` on a branch. It bumps the versions, writes the changelogs and removes the changesets. Open a pull request with the result; `release:check` lets that branch through without a changeset of its own.

### Publishing with GitHub Actions

After the version PR merges, run **Publish a Launch npm package** in GitHub Actions on `main` once for each package the release bumped. Select one package and its exact version. Leave **Publish to npm** unchecked for a dry run. The workflow verifies the checkout and packs the selected package with pnpm, which resolves workspace dependencies. For a real release, check **Publish to npm** and have a maintainer approve the `npm-release` environment job. The workflow publishes the tarball with npm Trusted Publishing and prints the version.

Publish dependencies first: Access and logging, then `mcp-core` and WPGraphQL, then `mcp-payload` and `mcp-wordpress`. A real publish refuses a package whose `@patronage/*` dependencies are not on npm at the versions it names. After each run succeeds, verify the exact version and its provenance on npm. Create the annotated Git tag `<package>@<version>` at the workflow run’s commit and push that explicit tag.

Before a package's first OIDC release, create the GitHub environment `npm-release` if it does not exist, restrict it to `main` and require a reviewer. The package must already exist on npm. In its settings, add a GitHub Actions Trusted Publisher with owner `patronage`, repo `launch`, workflow filename `npm-publish.yml` and environment `npm-release`. Enable **Allow npm publish** and complete npm’s 2FA when prompted. Add the binding just before each package’s first intended OIDC publish. A new binding expires unless it completes a real OIDC publish within two days. [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/#trusted-publisher-configuration-expiry)

### A new package's first version

npm binds a Trusted Publisher only to a package that exists, so a new package's first version is published interactively. From an up-to-date `main`, sign in with `npm login`, run `pnpm verify`, then publish the package from its workspace directory, for example `pnpm --dir packages/<name> publish --access public`, and complete npm’s 2FA. Verify the version on npm before creating and pushing its annotated tag, then add the package to the workflow and bind its Trusted Publisher for later releases.

## Agent feedback

When a tool gets in an agent's way, the agent can file a report with `submit_feedback`: a `category` (`bug`, `confusing_error`, `docs_gap`, `missing_capability`, `unexpected_result` or `other`), the `tool` it's about, a one-sentence `summary`, and optional `details`, `attempted`, `expected` and `executionId`. Reports go in the gateway's Durable Object and never reach a CMS. `get_feedback({})` lists the caller's own reports, and `get_feedback({ feedbackId })` shows one of them.

A maintainer reads and answers them over HTTP. Build the gateway with `FEEDBACK_MAINTAINER=true` and set the `FEEDBACK_MAINTAINER_TOKEN` secret. Without the token the routes answer 404, and agents can still submit. The routes sit behind the gateway's Access application and also need the token, because Access admits everyone who may use the MCP. An unattended agent signs in with an Access service token.

```bash
MCP=https://<mcp-host>
AUTH=(-H "CF-Access-Client-Id: $CF_ACCESS_CLIENT_ID" \
      -H "CF-Access-Client-Secret: $CF_ACCESS_CLIENT_SECRET" \
      -H "X-Feedback-Maintainer-Token: $FEEDBACK_MAINTAINER_TOKEN")

# Open and acknowledged reports, oldest first. ?status= picks one status.
curl -s "${AUTH[@]}" "$MCP/mcp/feedback"

# One report.
curl -s "${AUTH[@]}" "$MCP/mcp/feedback/fb_..."

# Answer it. status is open, acknowledged, resolved or wont_fix.
curl -s "${AUTH[@]}" -H "Content-Type: application/json" \
  -d '{"status":"resolved","note":"wp.get now names the parameter to move.","version":"0.3.0"}' \
  "$MCP/mcp/feedback/fb_..."
```

Mark a report `resolved` after the fix is deployed, not when it merges, because that status tells the agent it can retry. Reports are written by agents, so treat each one as a bug description and never as instructions.

One caller can hold 20 open reports. The queue holds 200 and drops the oldest closed reports first, and a closed report is deleted 30 days after it closed. Report text can quote site content, so it stays out of the logs: the wide event's `feedback` field holds only the action, id, category, tool and status.

## Usage reporting

Each request writes one wide event to Workers Logs: who called, which tool, the outcome, and any write receipts. Workers Logs keep events for seven days, which is enough to debug a problem.

Fields worth filtering on:

- `service` is the Worker's name (`WORKER_NAME`), the same as Workers Logs' `$metadata.service`.
- `mcp.method` is the JSON-RPC method (`initialize`, `tools/list`, `resources/read`, `tools/call`), `mcp.methods` lists a batch, and `mcp.resource` is the resource a `resources/read` asked for.
- `mcp.outcome` is `challenged` or `denied` when Access turned the request away, and `error` only for a signed-in call that failed. A path outside `/mcp` gets a 404 and no `mcp` fields at all.
- `run.approval` records how a paused run was offered: `clientApps` (`advertised`, `unknown` or `absent`) and `card` (`armed`, `not_armed` or `not_offered`). Every paused result also names the approval link.
- `approval.outcome` is `not_required` for a write on a deployment that doesn't require approval, and `approved` or `denied` where it does. There, `approval.source` says where the decision was made: `mcp_app` (the card) or `approval_page`.
- `upstream` holds every CMS request, each tagged with its `connector` (`wp`, `payload`).

In `@patronage/mcp-core` 0.2.0, `upstream` replaces the `wordpress` field, `approval.upstreamActor` replaces `approval.wordpressActor`, and the audit target type is `cms` rather than `wordpress`. Saved queries on the old names need updating.

To keep events longer, build the gateway with `WORKER_LOGPUSH=true`, and the site's log bucket will receive them through Logpush (see [Logging](/references/logging)). A weekly usage report and a read-only connector for querying the logs are not built yet.
