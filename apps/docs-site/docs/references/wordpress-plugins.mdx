Launch's WordPress plugins live in [`wordpress-shared/`](https://github.com/patronage/launch/tree/main/wordpress-shared), and any WordPress site can install them with Composer from `https://launch.patronage.com/composer`. They are mu-plugins, so they are always on, and each does nothing until its constants are set in `wp-config.php`.

| Package | What it does |
| --- | --- |
| `patronage/launch-access` | Locks WordPress behind Cloudflare Access, signs editors in from their Access login, and authenticates REST and WPGraphQL requests from a forwarded Access JWT. [README](https://github.com/patronage/launch/tree/main/wordpress-shared/patronage-access) |
| `patronage/launch-logging` | Records security events as wide events and ships them, with the host's log files, to the site's log bucket. See [Logging](/references/logging). [README](https://github.com/patronage/launch/tree/main/wordpress-shared/patronage-logging) |
| `patronage/launch-headless-revalidate` | Tells a headless front-end which paths and cache tags to revalidate when content changes. [README](https://github.com/patronage/launch/tree/main/wordpress-shared/patronage-headless-revalidate) |
| `patronage/launch-fleet` | For sites Patronage runs: reports WordPress, plugin and theme versions to Patronage Fleet for its vulnerability scan, and answers its uptime checks. [README](https://github.com/patronage/launch/tree/main/wordpress-shared/patronage-fleet) |

[`packages.json`](https://launch.patronage.com/composer/packages.json) lists every released version.

## Install

Add the repository and require what you need:

```json
{
  "repositories": [
    { "type": "composer", "url": "https://launch.patronage.com/composer" }
  ],
  "require": {
    "composer/installers": "^2.2",
    "patronage/launch-access": "^1.0"
  },
  "config": {
    "allow-plugins": { "composer/installers": true }
  }
}
```

Composer puts each plugin in its own folder, such as `wp-content/mu-plugins/patronage-access/`. WordPress loads only the files at the top of `mu-plugins/`, so add a one-line loader for each, and commit it:

```php
<?php
// wp-content/mu-plugins/patronage-access.php
require_once __DIR__ . '/patronage-access/patronage-access.php';
```

Where WordPress isn't in `wp-content/`, point `extra.installer-paths` for `type:wordpress-muplugin` at your mu-plugins folder. On Bedrock, which already does, its mu-plugin autoloader loads them, so no loader file is needed.

Updates are `composer update patronage/launch-access`. Each zip holds only the plugin's PHP and its license, so nothing in the webroot names its version.

## Releasing a new version

For contributors to Launch:

1. In the PR that changes a plugin, bump the `Version:` header in its main file, then run `pnpm wp:release <folder>`, such as `pnpm wp:release patronage-access`. It adds the version, with the zip's checksum, to `apps/docs-site/public/composer/packages.json` and its download redirect to `apps/docs-site/composer-redirects.txt`. Commit both.
2. `pnpm verify` fails if a plugin's files or `composer.json` change without a new release.
3. After the PR merges, run `pnpm wp:release --publish` from an up-to-date `main`. It creates the GitHub release `<package>-v<version>` (for example `launch-access-v1.0.0`) with the zip, using the `gh` CLI. The docs site deploys on merge, so the version is installable once both are done.

A released version is never rebuilt or replaced. The decision, including why the plugins are public, is [ADR 0017](https://github.com/patronage/launch/blob/main/docs/adr/0017-wordpress-plugins-through-composer.md).

## Security review coverage

Contributors can run `pnpm security:scan <commit>` from the repository root to discover security-review candidates in a committed snapshot. The setup covers the plugins' PHP, the release tool, the docs build script and headless deployment shell scripts. Package metadata, export rules, the Composer index, download redirects and install configuration are supporting review context; a snapshot containing them does not mean DeepSec analyzed them.

Security snapshots retain all tracked files, including files excluded from release zips by `export-ignore`, and verify their committed bytes. The candidate scan uses an isolated container with no network or model credentials and remains available. Model-backed review is disabled pending repair of the subscription runner's TLS destination boundary. Candidate counts are not findings or a security pass. See the [DeepSec workflow and limits](https://github.com/patronage/launch/blob/main/.deepsec/README.md) for prerequisites, evidence and cleanup of existing runners.
