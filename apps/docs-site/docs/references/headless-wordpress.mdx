Two apps make up this reference: [`cms-wordpress-headless`](https://github.com/patronage/launch/tree/main/apps/cms-wordpress-headless), WordPress in Docker as the editor and API, and [`web-wordpress`](https://github.com/patronage/launch/tree/main/apps/web-wordpress), the vinext front-end that deploys as a Worker.

## How it fits together

| Concern | WordPress | Front-end |
| --- | --- | --- |
| Content | WPGraphQL at `/graphql` | Typed queries generated from a committed schema snapshot |
| Locked queries | WPGraphQL Smart Cache runs only registered queries | Requests send a query ID, never query text |
| Revalidation | A Patronage mu-plugin sends the paths and tags that changed | A route handler calls `revalidatePath` and `revalidateTag` |
| Preview | The Preview button links to the front-end with a signed, short-lived token | Draft mode, reading the latest revision with the `X-GraphQL-Preview` header |

Pages are cached in KV until WordPress says they changed, with an hourly fallback. Each page carries cache tags for every post, term and menu it read, so editing one page expires that page and the pages that show it, and leaves the rest cached. Public pages stay cacheable because draft mode only runs on the preview route.

## Use it on another site

The front-end's WordPress plumbing is on npm, with no framework code in it, so a site on the App Router or the Pages Router can use it:

- **`@patronage/launch-wpgraphql`**: `createWordPressFetch` sends the Access service token (or nothing, for local Docker), refuses other origins, turns an Access login redirect into an error, verifies and forwards an editor's Access JWT for previews, and counts every read toward `upstream.wordpress`. `readGraphQLData` throws a `WordPressQueryError` for an HTTP error, GraphQL errors or a missing `data`, so a failed read is never cached. `persistedQueryId` and `persistedQueryBody` send a codegen document by its Smart Cache query ID, and `smartCacheTags` and `pathTag` turn a response's `X-GraphQL-Keys` and a path into cache tags.
- **`@patronage/launch-images`**: `serveImage` resizes a WordPress upload with the Cloudflare Images binding at `/media`, because vinext's `/_next/image` only resizes files in `public/` on Workers. `imagePath`, `imageSrcset` and `rewriteMediaUrls` point a page's images at that route. `cropSrc` asks the route for an aspect ratio cropped around a focal point (Cloudflare's `fit: "cover"` and `gravity`), so the CMS keeps only originals instead of pre-cut crop sizes; pass `signingKey` to `serveImage` and build URLs with `signedCropSrc` on the server so nobody can run up transforms the site never asked for.
- **`@patronage/launch-logging`**: `withRequestLog` wraps the Worker entry so each request prints one wide event, with vinext's cache result and the `upstream.wordpress` totals.

On the Pages Router, cache each public read with `unstable_cache` from `next/cache` under its Smart Cache tags, and run vinext's cache on KV (`kvDataAdapter`) so a revalidation reaches every isolate.

## Editing

The fields live in PHP and are shared with the [Timber install](/references/timber-wordpress) (see [ADR 0010](https://github.com/patronage/launch/blob/main/docs/adr/0010-wordpress-fields-in-php.md) and [ADR 0015](https://github.com/patronage/launch/blob/main/docs/adr/0015-shared-wordpress-fields.md)):

- **Hero**, on pages and posts, in the same five variants as Payload.
- **Page Builder**, on pages: one flexible content layout per section in the content model, each with a Section options tab. Pages hide the block editor; their content is their sections.
- **Rich text** takes the content model's blocks as shortcodes, such as `[launch_button]` and `[launch_embed]`. The shared fields plugin filters it with `wp_kses_post()` when it loads, so it cannot carry script.
- **Forms** are [Formidable Forms](https://wordpress.org/plugins/formidable/) (free). A form section exposes its form to WPGraphQL, and the front-end posts submissions to a REST route that only it can call. WordPress checks each value and saves the entry.

## What the research settled

- Install WPGraphQL from its GitHub release zips through Composer. Its Packagist package stopped at an old version.
- Preview with the `X-GraphQL-Preview` header. The `asPreview` argument is deprecated.
- Read drafts with a WordPress application password, so no JWT plugin is needed.
- Sign preview links instead of putting a shared secret in the URL.
- Lock WPGraphQL to the front-end's own queries, and keep that setting in git.

The detail is in [vinext on headless WordPress](/research/vinext-on-headless-wordpress).

## Run it

```bash
pnpm --filter cms-wordpress-headless run setup   # composer install, Docker, WordPress and demo content
pnpm --filter web-wordpress dev              # http://localhost:3000
```

The admin is at `http://localhost:8080/wp-admin/`. The local login is in the app's README. The install deploys to its host with the WordPress deploy kit; see [Deploying WordPress](/deploy/wordpress).

Both WordPress installs include the `patronage-logging` mu-plugin. It stays off until you configure it. See [Logging](/references/logging).
