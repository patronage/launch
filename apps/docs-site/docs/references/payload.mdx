The Payload reference is a single app: the Payload admin, plus front-end pages that read content through Payload's Local API in the same Worker. There is no separate API call between the front-end and the CMS. It runs Payload 4 (beta) under vinext on Cloudflare Workers, with media in R2.

## Database: Postgres on PlanetScale

**Decision (2026-11-13):** production Payload runs on the PlanetScale Postgres database `launch-payload` through Hyperdrive, because that is how most Launch sites will run. Until the move is done, the live demo still runs on D1, the 2026-10-29 choice. D1 stays the default for local work, since it needs no Docker. See [ADR 0020](https://github.com/patronage/launch/blob/main/docs/adr/0020-payload-production-on-planetscale.md), which replaces the database part of [ADR 0007](https://github.com/patronage/launch/blob/main/docs/adr/0007-payload-single-app-on-d1.md).

|  | D1 | Postgres through Hyperdrive |
| --- | --- | --- |
| Status | Local default; production until the move | Production, `PAYLOAD_DB=postgres` |
| Admin, uploads, drafts, REST and GraphQL | Pass | Pass |
| Migrations on boot and the Payload CLI | Pass | Pass |
| Extra work needed | None | A request-scoped connection pool (below) |

Both databases passed the same end-to-end browser test in local workerd, and their migrations build the same tables and columns. Postgres needs a connection pool that opens a connection per request, because workerd ties a socket to the request that opened it. Hyperdrive does the real pooling, through its managed PlanetScale integration, with query caching off so the admin always reads what it has just written.

`PAYLOAD_DB` is replaced at build time, so the unused adapter is left out of the bundle and `cloudflare.config.ts` declares only the matching binding.

### Moving from D1

`pnpm run hyperdrive:configure` creates the Hyperdrive configuration (or finds it) and prints its id. `pnpm d1:copy --target <postgres-url>` copies the D1 database into a freshly migrated Postgres with the same ids, reading D1 only, in one transaction that commits only when every table's row count matches. Sessions, document locks and the key-value cache aren't copied, so editors sign in again. Then the Workers Builds trigger builds with `PAYLOAD_DB=postgres` and `HYPERDRIVE_ID`. D1 is left as it was, so building without those two variables goes back. The app's README has the step-by-step switch.

## Pull content from PlanetScale

`pnpm db:pull` replaces the local Postgres with a copy of the content in the app's PlanetScale database, for working against real pages and posts. It needs Docker and the `pscale` CLI, signed in (`pscale auth login`) as someone who may manage roles on the database. From `apps/payload`:

```bash
pnpm db                        # start the local Postgres 17 (docker-compose.yml)
pnpm db:pull                   # copy PlanetScale's main branch
pnpm db:pull --branch staging  # or another branch
pnpm db:pull --migrate         # then run this checkout's pending migrations on the copy
pnpm db:pull --dry-run         # print the plan and contact nothing
```

Stop the preview server first, because the pull replaces the database it has open.

- **Read-only.** The pull creates a temporary PlanetScale role that can only read and expires after 30 minutes, dumps through it, and deletes it as soon as the dump ends, even when the run fails or is interrupted.
- **Content only.** `db-pull.tables` lists each table as `content`, whose rows are copied, or `excluded`. Users, sessions, admin preferences, form submissions and forms' notification emails are excluded and arrive empty, and so does any table the list doesn't name. The app's tests fail when a migration adds a table the list doesn't classify.
- **Checked before the swap.** The copy is restored into a scratch database and checked, then swapped in. A failed run leaves the local database as it was and says where everything is.
- **No users.** Open the admin on `localhost` and create the first user, which the local one-click sign-in then uses.
- **Migrations.** The run compares the copy's migrations with this checkout and with `origin/main`, and fails when the copy has run one this checkout lacks.

Media is not copied; it stays in R2. `pnpm db:recreate` deletes the local copy. The shared script is `packages/db-pull`, and its [README](https://github.com/patronage/launch/blob/main/packages/db-pull/README.md) covers the settings another app needs. See [ADR 0019](https://github.com/patronage/launch/blob/main/docs/adr/0019-local-pulls-copy-content-only.md).

## The demo

`pnpm seed` builds the same invented site as the WordPress seed, so the two references can be compared page by page.

- **Pages** hold a `layout` of blocks, one per section in the content model, each with a Section options tab (skin, width, padding, anchor, hidden). Field names match the WordPress page builder, so the Payload adapter only maps rich text, links and media.
- **Heroes** come in five variants, one of them free-form rich text.
- **Rich text** is Lexical, with blocks for buttons, images, pullquotes and video or X embeds.
- **News**: posts with authors and categories, listed at `/news`.
- **Forms** from Payload's form-builder plugin. A form section posts to the app, which keeps only the form's own fields, checks the required ones and saves the submission with the visitor's access. Email delivery is not wired up yet.
- **Preview**: pages and posts autosave drafts, and editors see them through the preview button and Live Preview, which re-renders on each autosave.
- **SEO and redirects**: the seed library has an editor-written title and description, the tool share is hidden from search engines, and two old addresses redirect.

On `localhost` only, the login page offers a one-click sign-in as the first user. It is hidden through a tunnel and on a deployed Worker.

On the deployed Worker, Cloudflare Access signs editors in: an editor who passes Access lands in the admin as the Payload user with the same email. **Log out** works as it does in the WordPress admin: it ends the CMS session but not the Access session, and shows the login form. From there the editor signs in with a password, or chooses **Sign in with Access as …** to go straight back in. For an hour after logging out, the admin keeps showing the form instead of signing the editor in automatically. WordPress's `patronage-access` plugin does the same from version 1.1.0. To end the Access session itself, visit `/cdn-cgi/access/logout`; Access ends it for every Access-protected app.

## Search and redirects

Editors control how a page or post appears to search engines, and where old addresses go.

- **SEO group.** Pages and posts have a title, description and social image from Payload's SEO plugin, plus **Hide from search engines**. An SEO title is used exactly as written. Without one, the document's title goes through the `Title | Site` template. An empty description falls back to a post's excerpt or the site tagline, and an empty image to the hero.
- **Canonical URLs** use the hostname of the request. A deployed Worker answers on one public hostname, so there is no site URL to configure.
- **`/sitemap.xml`** lists `/news` and every published page and post that isn't hidden, in one file.
- **`/robots.txt`** points to the sitemap and keeps crawlers out of `/admin/`, `/api/`, `/forms/` and `/next/`. On a `workers.dev` hostname it disallows everything, so Previews stay out of search results.
- **Redirects** are a collection in the admin, with a 308 (permanent) or 307 (temporary) status. The front end checks them only when nothing is published at a path, so a published page always wins and normal page views cost no extra read. A `from` path matches with or without a trailing slash, at any depth. Query strings aren't matched or carried over, and regular expressions aren't supported. A redirect to an unpublished document is ignored.

Metadata renders in `<head>` for every visitor. Next and vinext normally stream it into `<body>` except for a list of known bots, so `next.config.ts` sets `htmlLimitedBots` to match everyone. Crawlers that read only HTML then see it too.

## Deployed

The app runs as the Worker `launch-payload`, with its database (D1 until the move to PlanetScale) and R2 bucket. The first user can only be created on `localhost` or through Cloudflare Access, signed in with the same email, so a fresh deploy reached before Access protects it can't be claimed by someone else. Branch Previews are off by default, because they would share production's bindings; there is no PlanetScale staging branch yet. The app's README covers the deploy, secrets and Workers Builds setup.

## What else the research found

- `vite dev` does not work with Payload yet. Develop with `vite build` and `vite preview` until it does.
- Every Local API call made for a visitor passes the visitor's `user` and `overrideAccess: false` explicitly. Only trusted server code, such as seeding and migrations, overrides access.
- Front-end reads are wrapped in React's `cache()`, so the layout, the page and their `generateMetadata` share one auth check and one read of each document per request.
- There is no schema push on Workers. Every environment uses migrations, and the Worker applies pending ones on its first request.
- Image cropping and focal points are off, because there is no `sharp` on Workers.

The full write-up, with every check and workaround, is [Payload as one app under vinext on Workers](/research/payload-on-vinext).
