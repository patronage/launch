title: Workers Builds
description: How each app builds and deploys on push with Cloudflare Workers Builds, with Preview URLs for every branch and no GitHub Actions.
---

Each deployable app is connected to Cloudflare Workers Builds on its own, so a push to `main` deploys production and a push to any other branch deploys a Worker Preview named after the branch.

| Setting | Value |
| --- | --- |
| Root directory | the app folder, such as `apps/web-wordpress` |
| Watch paths | the app folder, `packages/*`, `pnpm-lock.yaml` and `pnpm-workspace.yaml`, so a change to another app does not rebuild this one |
| Build command | the workspace's frozen install check and lint, then typecheck and tests for the app and the packages it depends on (`pnpm --filter "<app>..."`), so a failing check stops the deploy |
| Production deploy | `pnpm run deploy`, on `main` |
| Preview deploy | `pnpm run deploy --preview`, on every other branch |
| Build variables | `NODE_VERSION` from `.nvmrc`, `PNPM_VERSION` from the root `packageManager`, `SKIP_DEPENDENCY_INSTALL=1` |

`SKIP_DEPENDENCY_INSTALL` is set because an app folder has no lockfile of its own; the build command installs from the workspace root instead. It runs less than the full `pnpm verify`, which also runs the WordPress installs' PHP checks, because the build image has no PHP. Run `pnpm verify` yourself before opening a pull request.

The Payload app builds production only by default. A Payload Preview never binds the production database or media bucket: to turn Previews on, create a separate D1 database and R2 bucket, set `WORKER_PREVIEWS=true` with `PAYLOAD_PREVIEW_D1_ID`, `PAYLOAD_PREVIEW_D1_NAME` and `PAYLOAD_PREVIEW_R2_BUCKET`, and put every Preview hostname behind Access. A Preview build without them fails instead of falling back to production. Payload is served only on its custom domain once `WORKER_DOMAIN` is set, because its Access application covers that hostname.

## Connect an app

Each app's `pnpm run builds:configure` creates this configuration through the Workers Builds API. Every call goes through `cf`, so your own `cf auth login` is enough; it needs no API token. It reads the Worker name from `cloudflare.config.ts` and the Node and pnpm versions from the repo, so the only inputs are ids.

1. Once for the repo, install the Cloudflare GitHub app on it from the dashboard. This is the only dashboard step.
2. Deploy once from your machine, so the Worker exists: `pnpm run deploy`.
3. Find the build token with `cf builds tokens list`, and the GitHub owner and repo ids. One build token serves every Worker in the account, so reuse the existing one. It belongs to whoever created it, and builds stop deploying if that person loses access. Creating one takes an API token's secret, so if the account has none, let the dashboard's Connect to Git flow create it.
4. Run `BUILD_TOKEN_UUID=… GITHUB_OWNER_ID=… GITHUB_REPO_ID=… pnpm run builds:configure`.
5. Push a branch and check that its Preview comes up, then merge and check production.

To keep a Worker's request logs, set `WORKER_LOGPUSH=true` before running `builds:configure`, so builds pass it on. See [Logging](/references/logging).

The same goes for the other settings an app reads at build time: `WORKER_NAME`, `WORKER_DOMAIN`, and the `ACCESS_*` values (Payload's `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` turn on its Access sign-in and let the deployed admin create its first user). Set them before running `builds:configure`, or later builds fall back to the defaults.

### Build variables live on the trigger

`builds:configure` copies the build variables onto the Worker's Builds trigger once, when it creates it. Changing your shell or `cloudflare.config.ts` afterwards does not reach the trigger. When an app starts reading a new variable at build time, add it to the trigger, or every Builds deploy sets it blank:

```bash
cf workers scripts search --name <worker>          # its "id" is the script tag
cf builds triggers list --external-script-id <tag> # the production trigger's trigger_uuid
cf builds triggers environment-variables list --trigger-uuid <uuid>
cf builds triggers environment-variables upsert <uuid> --body '{"NAME":{"value":"…","is_secret":false}}'
cf builds create <uuid> --branch main               # rebuild so the Worker picks it up
```

The Builds commands take the script tag, not the Worker name. A Builds deploy shows up as `cf_cli` in the Worker's deployment list, the same as a deploy from a laptop, so check `cf builds list --external-script-id <tag>` to see which deploys came from Builds.

Preview URLs are public by default. Put them behind Cloudflare Access along with the CMS.

A Preview runs whatever a branch contains, so treat its secrets as reachable by anyone who can push a branch. Give Previews Base their own values where the CMS allows it, rather than production's: a separate Access service token, added to the CMS's Access policy, and a preview-only WordPress user, so either can be revoked without touching production. Export those before running `pnpm run secrets --preview-base`.
