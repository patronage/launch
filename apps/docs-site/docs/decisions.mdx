Every choice the rest of the repo must follow is an architecture decision record (ADR) in the repo's [`docs/adr`](https://github.com/patronage/launch/tree/main/docs/adr) folder, beside the engineering docs for contributors and agents. This page summarizes them and links to each record. A record that changes an earlier one supersedes it rather than editing it.

## Made

| Area | Decision |
| --- | --- |
| Repo | One public monorepo with no vendor code and no client references. See [ADR 0001](https://github.com/patronage/launch/blob/main/docs/adr/0001-public-reference-monorepo.md). |
| Hosting | Every front-end and the MCP server run on Cloudflare Workers. |
| Front-end framework | vinext, Cloudflare's Vite-based implementation of the Next.js App Router. See [ADR 0005](https://github.com/patronage/launch/blob/main/docs/adr/0005-vinext-front-ends-on-workers.md). |
| Worker config | `cloudflare.config.ts` and the `cf` CLI. No Wrangler config files in the repo. See [ADR 0003](https://github.com/patronage/launch/blob/main/docs/adr/0003-cloudflare-config-through-cf-cli.md). |
| Verification and deploys | Run `pnpm verify` before opening a pull request. Cloudflare Workers Builds handles deployments and branch Previews. See [ADR 0025](https://github.com/patronage/launch/blob/main/docs/adr/0025-npm-trusted-publishing.md). |
| npm publishing | A manual GitHub Actions workflow publishes every npm package (Access, images, logging, WPGraphQL and the MCP packages) through npm Trusted Publishing. See [ADR 0025](https://github.com/patronage/launch/blob/main/docs/adr/0025-npm-trusted-publishing.md) and the [release guide](/references/mcp#releasing-the-npm-packages). |
| Monorepo tooling | Plain pnpm workspaces, no Turborepo. Exact versions, one shared version (a pnpm catalog) for dependencies most packages use, and a minimum release age before a version installs. See [ADR 0002](https://github.com/patronage/launch/blob/main/docs/adr/0002-plain-pnpm-workspaces.md). |
| WordPress | Two separate installs: headless over WPGraphQL, and a traditional Timber theme. They share their fields, post types and seed. See [ADR 0006](https://github.com/patronage/launch/blob/main/docs/adr/0006-separate-wordpress-installs.md) and [ADR 0015](https://github.com/patronage/launch/blob/main/docs/adr/0015-shared-wordpress-fields.md). |
| WordPress fields | Field groups in PHP with Extended ACF on Secure Custom Fields, post types with Extended CPTs. See [ADR 0010](https://github.com/patronage/launch/blob/main/docs/adr/0010-wordpress-fields-in-php.md). |
| WordPress plugins | Installed by Composer and never committed. Only Patronage's own `patronage-*` code is in the repo. |
| Patronage plugins for other sites | Access, Logging, Headless Revalidate and Fleet install with Composer as `patronage/launch-*` from `https://launch.patronage.com/composer`, with zips on GitHub releases. Published because Cloudflare Access, not hidden code, is what protects a site. See [ADR 0017](https://github.com/patronage/launch/blob/main/docs/adr/0017-wordpress-plugins-through-composer.md) and [WordPress plugins](/references/wordpress-plugins). |
| WordPress deploys | One deploy kit, `wp-deploy`, pushes a packaged commit to the host. See [ADR 0013](https://github.com/patronage/launch/blob/main/docs/adr/0013-wordpress-deploy-kit.md) and [Deploying WordPress](/deploy/wordpress). |
| Payload | One app, using the Local API. See [ADR 0007](https://github.com/patronage/launch/blob/main/docs/adr/0007-payload-single-app-on-d1.md) and [Payload](/references/payload). |
| Payload database | Launch supports D1 and Postgres, chosen with `PAYLOAD_DB`; D1 is the default. The demo's production runs on Postgres on PlanetScale through Hyperdrive (managed integration, caching off), moved from D1 with `pnpm d1:copy`, which only reads D1. D1 stays the local default. Previews share one PlanetScale `preview` branch: the shared copy in `public`, or a schema of the branch's own when it adds migrations ([ADR 0021](https://github.com/patronage/launch/blob/main/docs/adr/0021-payload-previews-on-one-preview-database.md)). See [ADR 0020](https://github.com/patronage/launch/blob/main/docs/adr/0020-payload-production-on-planetscale.md) and [Payload](/references/payload#database-d1-or-postgres). |
| Local data | `pnpm db:pull` copies the content of a PlanetScale Postgres branch into a local Postgres, through a temporary read-only role. Only tables listed as content are copied; users, sessions and form submissions never leave PlanetScale. See [ADR 0019](https://github.com/patronage/launch/blob/main/docs/adr/0019-local-pulls-copy-content-only.md) and [Payload](/references/payload#pull-content-from-planetscale). |
| EmDash | One Astro app on one Worker renders the site with the shared sections and serves the EmDash admin and API. Previews, redirects and SEO are EmDash's own, forms come from its forms plugin, and the admin is behind Access. News stories use EmDash's category and tag taxonomies, one category per story, with category images in a separate collection; listings load more through a public route, not the CMS API ([ADR 0026](https://github.com/patronage/launch/blob/main/docs/adr/0026-emdash-news.md)). See [ADR 0024](https://github.com/patronage/launch/blob/main/docs/adr/0024-emdash-seo-redirects-and-forms.md), [ADR 0022](https://github.com/patronage/launch/blob/main/docs/adr/0022-emdash-renders-the-site-in-astro.md) and [EmDash](/references/emdash). |
| Shared UI | Plain props from a CMS-neutral content model, on shadcn/ui and Tailwind 4. Each CMS has an adapter; rich text stays CMS-specific. See [ADR 0008](https://github.com/patronage/launch/blob/main/docs/adr/0008-cms-neutral-content-model.md), [ADR 0009](https://github.com/patronage/launch/blob/main/docs/adr/0009-shadcn-ui-package.md) and [Shared UI](/references/ui). |
| Access | Every CMS admin and API is behind Cloudflare Access. Front-ends read with a service token, which can only read. See [ADR 0011](https://github.com/patronage/launch/blob/main/docs/adr/0011-cms-behind-cloudflare-access.md). |
| MCP | One MCP gateway Worker per site, behind Access, with WordPress, Payload and EmDash connectors. Writes run as the signed-in person; a site that needs it sets `APPROVAL_REQUIRED=true` to hold them for Approval ([ADR 0023](https://github.com/patronage/launch/blob/main/docs/adr/0023-approval-is-opt-in.md)). The packages are published to npm and versioned with Changesets. See [ADR 0014](https://github.com/patronage/launch/blob/main/docs/adr/0014-mcp-gateway-worker.md) and [MCP server](/references/mcp). |
| MCP writes to Payload | The Payload connector writes through Payload's REST API as the signed-in person (or approver where Approval is required), and Payload's own MCP server stays read-only. Beyond drafts it uploads media, changes single rows of blocks and arrays, updates globals, unpublishes, restores versions, uses the trash and writes one locale of a site that has several. It never deletes permanently. See [ADR 0018](https://github.com/patronage/launch/blob/main/docs/adr/0018-payload-connector-writes.md). |
| MCP on EmDash | The EmDash connector reads EmDash's REST API as the signed-in editor, from an allowlist that leaves out users, tokens, settings and plugins, because EmDash's own MCP endpoint takes only OAuth or API tokens. EmDash trusts the editor's forwarded Access JWT only with the gateway proof. Writes save drafts, add draft entries and publish, each on the `_rev` the model read ([ADR 0027](https://github.com/patronage/launch/blob/main/docs/adr/0027-emdash-connector.md)) |
| Logging | Each site's logs are files in one R2 bucket: Workers through Logpush, WordPress through a Basin Pipelines stream. Optional and off until configured. Reading and acting on the logs is outside Launch. See [ADR 0016](https://github.com/patronage/launch/blob/main/docs/adr/0016-logs-to-r2-through-logpush.md) and [Logging](/references/logging). |
| Docs | This site, built with Blume, for readers of Launch. Engineering docs, including the decision records, stay in the repo's `docs/` folder; the research notes publish here from `docs/spikes`. |
